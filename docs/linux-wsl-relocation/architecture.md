# Relocation architecture

`backend.season_simulation.relocation` owns offline verification of the version-1 continuation-subset layout. A caller supplies an independently trusted SHA-256 for `transfer-manifest.json`; the existing archive verification is its provenance. The tool validates the complete imported inventory, frozen runtime, operator/target/preview proofs, source assets and retained generation/revision lineage. It never executes an imported script or opens an imported database.

A relocation record binds that manifest and historical campaign hash to explicit absolute Linux locations. Original Windows path strings remain in the campaign and target proof; they are never passed through native path resolution. Consumers resolve only declared relative assets beneath the verified data root. No relocated campaign or rewritten progress file is generated.

The record also contains the observed runtime at the archived source root and a fingerprint of the adapter's current application source. Verification requires an independently retained record digest, rechecks the entire evidence tree and compares current measurements exactly. This detects later path, source, dependency, configuration, pricing and interpreter drift. Differences from the historical runtime are recorded explicitly, not accepted as execution-compatible. A verified record means repeatable offline inspection only. The existing controller and `assert_runtime` keep their strict behavior; this command does not expose a replacement verifier or a live-run flag.

Retained tables feed the existing controller reconciliation logic through a read-only evidence view. Table identity/competition/sequence/manifest checks reject ambiguous evidence before reconciliation. This validates the retained boundary, not the missing full memory contents, live target, runtime behavioral equivalence or article quality. Indexing receipts establish only their retained canonical boundaries.

New records are written exclusively, privately and outside the import tree. Full records may contain private source identifiers and physical paths; keep them outside tracked files. CLI summaries contain counts, hashes, next retained step and changed runtime field names, never narrative content, credentials or target login details.
